# Техническое задание
# CryptoTiles — компактный монитор криптовалют

## 1. Цель проекта

Разработать компактное приложение для мониторинга котировок криптовалют,
по концепции похожее на старый интерфейс TabTrader.

Основная идея:
- максимальная информационная плотность;
- котировки представлены небольшими плитками;
- 2 плитки в ряд на смартфоне;
- внутри каждой плитки текущая цена и мини-график;
- нажатие открывает подробный график;
- пользователь может создавать несколько экранов (tabs) с разными
  наборами инструментов.

Приложение предназначено только для мониторинга рынка.

НЕ реализовывать:
- торговлю;
- выставление ордеров;
- подключение аккаунтов бирж;
- кошельки;
- регистрацию пользователей;
- backend;
- cloud sync.


## 2. Целевые платформы

Одна кодовая база должна работать как:

1. Web application.
2. PWA на iPhone/iPad через Safari.
3. PWA на Android.
4. Android APK.

Для Android использовать Capacitor.

Исходный React-код не должен различаться между Web/PWA и Android.


## 3. Технологический стек

Использовать:

- React
- TypeScript
- Vite
- PWA
- Capacitor
- Lightweight Charts для основного финансового графика
  либо другую действительно подходящую lightweight-библиотеку.

Не использовать тяжелый UI framework без необходимости.

Интерфейс должен быть mobile-first.


## 4. Общая архитектура

Проект разделить как минимум на:

src/
  components/
  pages/
  hooks/
  services/
  providers/
  storage/
  types/

Сетевые запросы НЕ размещать непосредственно внутри React components.

Основная схема:

UI
 ↓
hooks / services
 ↓
MarketDataProvider
 ↓
конкретный источник котировок


## 5. MarketDataProvider

Приложение НЕ должно быть архитектурно привязано к Binance,
CoinGecko, CoinMarketCap, Bybit, OKX или другому конкретному API.

Создать abstraction layer:

MarketDataProvider

Он должен предоставлять операции уровня:

- searchAssets(query)
- getQuote(symbol)
- getQuotes(symbols)
- getHistory(symbol, range)
- subscribeQuotes(symbols)

Конкретные TypeScript types/interfaces спроектировать самостоятельно.

Архитектура должна позволять в будущем менять или добавлять
источники данных без изменения UI.

Также предусмотреть два механизма обновления:

- WebSocket;
- polling fallback.

ВАЖНО:
в первой итерации реальный cryptocurrency API пока НЕ подключать.

Создать MockMarketDataProvider, чтобы весь интерфейс можно было
разработать и протестировать независимо от будущего API.


## 6. Базовая валюта

Базовая валюта приложения фиксирована:

USDT

Все инструменты визуально представлены как:

BTC/USDT
ETH/USDT
SOL/USDT
и т.д.

Пользователь выбирает только базовый crypto asset.

Выбор USD/EUR/BTC и других quote currencies пока НЕ нужен.


## 7. Главный экран

Основной экран представляет собой максимально плотную сетку
небольших плиток котировок.

На смартфоне:

2 плитки в ряд.

Не делать большие Material-style cards с огромными отступами.

Основная идея дизайна:
как можно больше полезной информации на экране.

Ориентир по концепции — старый TabTrader.

Темная тема должна быть основной.


## 8. Содержимое плитки

Каждая плитка показывает:

- SYMBOL/USDT;
- текущую цену;
- изменение цены в процентах;
- небольшой sparkline;
- sparkline показывает движение цены за последние 15 минут.

Например:

┌─────────────────┬─────────────────┐
│ BTC/USDT        │ ETH/USDT        │
│ 112430.50       │ 4238.12         │
│   ╱╲__╱╲___     │ __╱╲___╱╲      │
│ +1.24%          │ -0.31%          │
├─────────────────┼─────────────────┤
│ SOL/USDT        │ LTC/USDT        │
│ 238.51          │ 117.32          │
│ __╱╲___╱╲       │ ╲___╱╲___      │
│ +3.18%          │ +0.72%          │
└─────────────────┴─────────────────┘

Sparkline:
- без осей;
- без подписей;
- без лишних элементов;
- line chart;
- предназначен только для быстрого визуального понимания движения цены.


## 9. Обычное нажатие на плитку

Короткое нажатие:

открывает отдельный экран выбранного инструмента.

Например:

BTC / USDT

112430.50
+1.24%

┌──────────────────────────────────┐
│                                  │
│          MAIN CHART              │
│                                  │
└──────────────────────────────────┘

[15m] [30m] [1h] [1d] [1w] [1M] [1Y]


## 10. Периоды графика

Поддержать:

15m
30m
1h
1d
1w
1M
1Y

ВАЖНО:

это диапазон отображаемой истории, а не обязательно candle interval.

Приложение должно самостоятельно выбирать подходящую детализацию
исторических данных.

Ориентировочно:

15m -> 1 minute
30m -> 1 minute
1h  -> 1 minute
1d  -> 5/15 minute
1w  -> hourly
1M  -> several-hour / daily
1Y  -> daily

Эту логику вынести из UI, чтобы впоследствии можно было изменить.


## 11. Основной график

График должен быть удобен на touch screen.

Требования:

- pan;
- zoom;
- touch gestures;
- отображение времени;
- отображение цены;
- корректная работа в portrait режиме смартфона;
- адаптация к размеру экрана.

На первом этапе достаточно line chart.

Архитектура не должна мешать впоследствии добавить candlestick chart.


## 12. Экраны / Tabs

Главный watchlist состоит не из одного списка, а из нескольких
независимых экранов.

Максимум:

5 экранов/tabs.

Каждый экран:

- содержит максимум 20 плиток;
- имеет собственный набор активов;
- имеет собственный порядок плиток;
- имеет уникальный ID;
- может иметь пользовательское название.

Пример:

[ Main ] [ DeFi ] [ Meme ] [ Long ]

или:

[ 1 ] [ 2 ] [ 3 ] [ 4 ] [ 5 ]


## 13. Переключение экранов

Пользователь должен иметь возможность переключать экраны:

1. нажатием на tab;
2. горизонтальным swipe.

Swipe должен быть естественным на iPhone и Android.

Он не должен мешать обычной вертикальной прокрутке страницы.

Если взаимодействие swipe конфликтует с drag & drop в edit mode,
в edit mode swipe между страницами можно временно отключать.


## 14. Управление экранами

Пользователь должен иметь возможность:

- создать новый экран;
- максимум 5 экранов;
- переименовать экран;
- удалить экран;
- переключаться между экранами.

Удаление экрана должно требовать подтверждения.

Активный экран должен сохраняться между запусками приложения.


## 15. Ограничение количества плиток

Один экран содержит максимум:

20 инструментов.

Это НЕ означает, что все 20 обязательно должны физически помещаться
без прокрутки.

При необходимости экран вертикально прокручивается.

Таким образом максимальная емкость:

5 screens × 20 assets = 100 инструментов.


## 16. Edit mode

Необходимо реализовать специальный режим редактирования плиток.

Долгое нажатие (long press) на любую плитку:

включает Edit Mode.

Long press НЕ должен сразу удалять плитку.


## 17. Возможности Edit Mode

В режиме редактирования пользователь может:

1. менять порядок плиток drag & drop;
2. удалить плитку;
3. перенести плитку на другой tab;
4. выйти из Edit Mode.

Должно быть визуально понятно, что приложение находится
в Edit Mode.

Например:

- появляется кнопка удаления;
- появляется drag handle;
- плитки немного меняют оформление;
- сверху появляется кнопка "Done".

Конкретный UI выбрать самостоятельно, сохраняя компактность.


## 18. Drag & Drop

Пользователь должен иметь возможность переставить плитки.

Например:

BTC ETH
SOL LTC

можно переставить в:

BTC SOL
ETH LTC

После завершения drag & drop новый порядок должен немедленно
сохраняться локально.

После перезапуска приложения порядок должен сохраниться.


## 19. Перемещение между экранами

В Edit Mode должна существовать команда:

Move to screen...

После ее выбора показать список существующих экранов.

Например:

Move BTC to:

Main
DeFi
Long
Other

После выбора актив удаляется с текущего экрана и появляется
на выбранном.

Позицию на новом экране можно первоначально делать последней.


## 20. Добавление инструмента

На основном экране должна существовать компактная кнопка "+".

Она открывает поиск.

Пользователь вводит, например:

DOG

и получает подходящие активы.

После выбора актив добавляется на текущий экран.

Не позволять случайно добавить один и тот же инструмент дважды
на один экран.

На разных экранах один инструмент может присутствовать.


## 21. Первый запуск

При первом запуске автоматически создать один экран:

Name: Main

Начальный набор инструментов, строго в таком порядке:

1. BTC/USDT
2. ETH/USDT
3. SOL/USDT
4. LTC/USDT
5. GRAM/USDT
6. TRX/USDT
7. BNB/USDT
8. XRP/USDT

Это только initial/default state.

После первого запуска пользователь может:

- удалить любой инструмент;
- добавить другой;
- изменить порядок;
- перенести его;
- создать дополнительные экраны.

ВАЖНО:

после инициализации приложения default watchlist больше автоматически
не восстанавливать.

Если пользователь удалил BTC, приложение не должно вернуть BTC
при следующем запуске.


## 22. GRAM

В initial watchlist должен присутствовать:

GRAM/USDT

Под GRAM пользователь имеет в виду Gram, связанный с бывшим
Telegram Open Network / TON ecosystem.

На этапе MockMarketDataProvider использовать symbol GRAM.

При последующем подключении реального market-data API НЕ выбирать
автоматически первый найденный токен с ticker GRAM.

Перед mapping реального GRAM отдельно проверить точный asset ID
у выбранного provider, потому что ticker может быть неоднозначным.


## 23. Локальное хранение

Backend отсутствует.

Вся пользовательская конфигурация хранится локально.

Хранить:

- список экранов;
- ID экранов;
- названия экранов;
- порядок экранов;
- активный экран;
- список assets каждого экрана;
- порядок assets;
- факт первоначальной инициализации;
- необходимые UI preferences.

Можно использовать localStorage или IndexedDB.

Выбрать вариант, который не усложняет приложение без необходимости.

Обязательно предусмотреть version поля структуры данных, чтобы
в будущем можно было мигрировать сохраненные настройки.


## 24. Модель состояния

НЕ проектировать приложение вокруг одного массива watchlist.

Логическая структура должна быть примерно:

Workspace
 ├── version
 ├── activeScreenId
 └── screens[]
      ├── id
      ├── name
      ├── position
      └── assets[]
           ├── symbol
           └── position

Конкретные TypeScript interfaces разработать самостоятельно.

Модель должна быть рассчитана на дальнейшее развитие приложения.


## 25. PWA

Приложение должно быть полноценным PWA.

Необходимо:

- manifest;
- service worker;
- application icons;
- standalone display mode;
- корректная viewport configuration;
- поддержка установки на Home Screen;
- корректная работа на iPhone Safari;
- корректная работа на Android Chrome.

При запуске с Home Screen приложение должно выглядеть максимально
похоже на standalone application, а не обычную web-страницу.


## 26. Android

Использовать Capacitor.

Подготовить Android project.

После:

npm build

должна существовать понятная процедура:

build React
→ Capacitor sync
→ Android build
→ APK

Не создавать отдельную Android UI implementation.

React UI является единственным UI приложения.


## 27. Responsive design

Основной target:

portrait smartphone.

Но приложение должно нормально открываться:

- на iPhone;
- Android;
- tablet;
- desktop browser.

На телефоне основной layout:

2 columns.

Не увеличивать автоматически плитки до огромного размера
на широких экранах.

На desktop допустимо увеличение количества columns.


## 28. Производительность

Учесть, что одновременно может существовать:

до 20 visible quote tiles.

Каждая имеет:

- текущую цену;
- процент изменения;
- 15-minute sparkline.

Не создавать отдельный независимый network request loop
для каждой React-плитки.

Market data должен получать service/provider layer,
после чего централизованно распространять состояние в UI.

Избегать ненужного полного rerender всей сетки при изменении
цены одного инструмента.

Архитектура должна быть рассчитана на realtime updates.


## 29. Работа при временной потере сети

Приложение не должно ломаться при отсутствии интернета.

Если данные временно недоступны:

- UI остается доступным;
- watchlist остается доступным;
- настройки не теряются;
- отображается состояние stale/offline;
- после восстановления сети данные продолжают обновляться.

Не требуется полноценный offline market-data cache.
